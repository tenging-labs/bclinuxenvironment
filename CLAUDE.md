# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A single cross-platform PowerShell 7.2+ script, `Invoke-BcLinuxEnvironment.ps1`, that creates a Business Central
environment with Docker or Podman Compose on Windows, Linux and macOS. It then publishes `.app`
extensions in a given order. It wraps upstream
[MsDyn365Bc.On.Linux](https://github.com/aldevtools/MsDyn365Bc.On.Linux) (BC service tier patched to run
on Linux) and **must keep using upstream's compose files**: the user prefers that over driving
`docker run` directly. User-facing usage lives in `README.md`; findings, work in progress and backlog
live in `docs/ROADMAP.md`. Keep both in sync when behaviour changes. In particular, the README
settings table must list every parameter and env-file key.

## Commands

There is no build, linter or unit-test suite. Validation is a parse check plus a real end-to-end run.

```bash
# Parse check (run after every edit)
pwsh -NoProfile -Command '$e=$null;$null=[System.Management.Automation.Language.Parser]::ParseFile("$PWD/Invoke-BcLinuxEnvironment.ps1",[ref]$null,[ref]$e); if($e){$e}else{"parse OK"}'

# End-to-end run (≈9 min with large ISV apps: ~3 min boot, ~6 min publish). Run it in the background.
# Use a personal, git-ignored *.local.env (license + APPS) if present, else example.env.
pwsh -NoProfile -File ./Invoke-BcLinuxEnvironment.ps1 -EnvFile ./example.env [-Recreate]

# Tear down (compose down -v + label-based cleanup + ~/.bcvm/<Name>)
pwsh -NoProfile -File ./Invoke-BcLinuxEnvironment.ps1 -Name bc285 -Remove

# Manage a running environment directly (the script prints this command; macOS overlay only on ARM)
docker compose -p bc285 -f ~/.bcvm/MsDyn365Bc.On.Linux/docker-compose.yml \
  -f ~/.bcvm/MsDyn365Bc.On.Linux/docker-compose.macos.yml -f ~/.bcvm/bc285/compose.override.yml \
  --env-file ~/.bcvm/bc285/compose.env <ps|stop|start|restart bc|logs -f bc>

# Readiness and extensions (default login BCRUNNER / Admin123!)
curl -s -u 'BCRUNNER:Admin123!' http://localhost:7048/BC/ODataV4/Company
# automation API: companies(<id>)/extensions — note isInstalled is NOT filterable server-side
```

To read upstream behaviour (env vars, entrypoint steps, publish rules), look at the cached clone in
`~/.bcvm/MsDyn365Bc.On.Linux`: `docker-compose.yml`, `docker-compose.macos.yml`,
`scripts/entrypoint.sh`, `scripts/publish-app.sh`, `KNOWN-LIMITATIONS.md`.

## Script architecture

**The script must stay one self-contained file.** Developers run it straight from the public
GitHub repo (raw.githubusercontent.com, no auth) as an in-memory script block (README "Run without cloning"), so it must not depend
on sibling files, `$PSScriptRoot`/`$PSCommandPath`, or `Get-Help` output. Anything it needs, such as
the FTS Dockerfile planned in the roadmap, has to be embedded or generated by the script.
Relative paths resolve against `$PWD` (or the env file's folder), never the script's location.

- **Never use `$script:` variables.** In script-block mode `$script:` is the caller's scope, so
  reads fail ("variable '$script:n' cannot be retrieved") and writes leak into the user's session.
  Shared state for helper functions lives in the `$ctx` hashtable; functions read it through
  normal scope lookup and mutate it in place.
- **Test both modes.** Run the script as a file, and as
  `& ([scriptblock]::Create((Get-Content -Raw ./Invoke-BcLinuxEnvironment.ps1))) <params>`. The run must
  get past `compose config/pull/up` (and `-Remove` on a real environment) to cover the helper
  functions. Stopping at validation proves only parameter binding.

The script runs top to bottom in sections:

1. Settings resolution (plus the existing environment's `compose.env` in non-create modes, and the
   pinned settings of `-FromSnapshot`/`-FromClone`)
2. Engine and compose detection
3. Remove
4. Helpers (readiness, SQL, BC API, publish, backup/restore, volume copy, router files)
5. Mode dispatch: `-List`, `-RemoveSnapshot`, `-RemoveClone`, and on an existing environment
   `-Snapshot`, `-Clone`, `-RestoreSnapshot`, `-ListApps`, app actions — each ends with `return`
6. Validation
7. Create only (`if ($mode -eq 'Create')`, not indented because it holds here-strings): upstream repo,
   generated compose files, clone volume copies, snapshot restore (SQL first), start
8. Wait, background-task fixes, extensions, company/packages (Create and `-Update`)
9. Summary

`$mode` is `$PSCmdlet.ParameterSetName`. Helper functions must be defined before the dispatch, since
PowerShell defines a function only when execution reaches it.

Cross-cutting rules:

- **Settings precedence:** `$defaults` < `-EnvFile` < `BCVM_<KEY>` env vars < bound parameters.
  - `$keyMap` maps env-file keys (upstream's names, e.g. `BC_LICENSE_HOST_PATH`) to setting names.
  - `ConvertTo-Setting` handles typing (bool/int/`;`-lists).
  - Unknown env-file keys and `-ContainerEnv` are passed straight to the BC container.
  - Adding a setting means touching: `param()`, `$defaults`, `$keyMap`, `ConvertTo-Setting` (if
    typed), the compose env/override generation, and the README table.
- **Ports and names:** default publishes all ports. `-PortlessRouter` (Kiri only, throws elsewhere)
  overrides upstream's `ports:` with `!override [...]` (only explicitly given ports, e.g. `-SqlPort`)
  and adds the nginx `router` service (generated `~/.bcvm/<Name>/router.conf`, label
  `dev.kiri.domain`) for `dev./odata./api./client.<Name>.kiri.local`. The user wants no router
  unless asked for, hence one switch. On Kiri (`docker info` OperatingSystem `Kiri`; its
  `ServerVersion` is the Docker API version, not Kiri's) the bc container always gets label
  `dev.kiri.http.port: 8080`, so `bc.<Name>.kiri.local` is the web client. Kiri routes a name to
  exactly ONE container port, HTTP on 80/443 only; `*.kiri.local` resolves to 127.0.0.1, so
  `name.kiri.local:7048` is just localhost:7048 (verified 2026-11-16). Kiri's name router closes a
  request after 30 s without an answer if the backend reads from the connection meanwhile (nginx
  does); the router config's `proxy_ignore_client_abort on;` stops nginx reading, which removes the
  cut — keep it. Kiri's published ports cut idle connections at 300 s.
  Readiness, extension and package calls from the script run curl **inside** the bc container,
  never via host ports.
- **Progress status:** `$status` (ordered dict, script scope like `$cfg`; set only after the
  "already exists" check) is mirrored to `~/.bcvm/<Name>/www/status.json` by `Save-Status` (temp file +
  `Move-Item`, atomic). `Write-Step` starts a step, `Write-Note`/`Write-Warning` (shadowed) append to
  `log`, `Set-StatusDetail` sets progress inside a step, a script-level `trap` marks `failed` and
  rethrows. With `-PortlessRouter` the router serves the folder at `<Name>.kiri.local`
  (`/api/status` + the embedded `$statusPageHtml`). Mount folders, never single files (atomic
  replace = new inode). Keep `schema` and field names stable: agents depend on them.
- **Switch values from other shells:** `pwsh -File` accepts `-Switch:false`; unquoted `-Switch:$false`
  in zsh/bash arrives as `-Switch:` and PowerShell silently ignores it, so the script throws on any
  `-Name:` command-line argument with an empty value. Inside PowerShell only `:$false` works.
- **Compose layering:**
  - Files: upstream `docker-compose.yml`, plus `docker-compose.macos.yml` when emulated, plus the
    generated `~/.bcvm/<Name>/compose.override.yml`.
  - `--env-file ~/.bcvm/<Name>/compose.env` passes settings by upstream variable names.
  - The file list is persisted in `compose-files.txt` so `-Remove` uses the same set.
  - The project name is `-Name`; containers are found by `com.docker.compose.*` labels, not by
    fixed names.
- **Generated file quoting:**
  - `compose.env` values are single-quoted, so compose does not interpolate `$`; values with
    `'` are rejected.
  - YAML scalars are emitted as JSON strings with `$` doubled.
  - The SQL tmpfs is removed with `tmpfs: !reset []`, which needs Compose ≥ 2.24.
- **`Invoke-Engine` / `Invoke-Compose` must stay plain functions using `$args`.** As advanced
  functions with `ValueFromRemainingArguments`, PowerShell binds engine flags like `-a` to itself
  ("positional parameter cannot be found").
- **Emulation:**
  - Detected from the host OS architecture or the engine architecture; `bc-runner` is
    `linux/amd64` only.
  - When emulated, the script adds upstream's macOS overlay (SQL 2022 CU17).
  - It also injects `DOTNET_INTERNAL_ThreadSuspendInjection=0` and `DOTNET_GCHeapCount=2`.
    Without them the NST crashes under Rosetta with `rt_tgsigqueueinfo failed` (exit 133).
- **Readiness** requires both `/tmp/bc-ready` in the BC container **and** an OData `/Company` answer.
  The marker survives a container restart until the entrypoint clears it, so never trust it alone.
- **Extension publish:**
  - Endpoint: dev endpoint `.../BC/dev/apps?SchemaUpdateMode=forcesync`, in the given order.
  - **Posted from inside the bc container**, never from the host: `docker cp` the app and a small
    `publish.sh` to `/tmp/bcvm-publish`, `docker exec -d` it (curl to `localhost:7049`, auth via
    `BCVM_AUTH` env), poll `<app>.code`. Kiri's port forwarding cuts connections idle for 300 s,
    and BC then cancels and rolls back the publish (LS Central takes longer than that).
  - Success: HTTP 200, or a benign 422, using the same regex as upstream `publish-app.sh`.
  - Dependency-looking failures are deferred and retried in another pass; anything else throws.
- **Version `latest`** (default) is resolved by the script from the public artifact index
  (`bcartifacts-…azurefd.net/<type>/indexes/<country>.json`, newest `Version`), because upstream only
  resolves prefixes. The full build goes into `compose.env`.
- **Persistence:** SQL data lives in the `sql-data` volume (SQL runs as `0:0`). The upstream
  entrypoint reuses an existing `CRONUS` DB, so stop/start keeps installed apps.
- **Snapshots (`~/.bcvm/snapshots/<snap>`):** `BACKUP … COPY_ONLY, COMPRESSION` in the sql container,
  copied out; `snapshot.json` pins the exact build read from `/bc/artifacts/.bc-artifact-cache` (the
  `key=` line). `-FromSnapshot` runs `compose up sql`, restores, then `up`; `Restore-BcDatabase` also
  clears the user's Windows Security ID before the tier starts.
- **Clones (`bcvm-clone-<clone>-<volume>` volumes + `~/.bcvm/clones/<clone>/clone.json`):** volumes
  are found through the containers' mounts (not labels), copied with `run --rm … cp -a` using the
  runner image. The clone keeps the source's `compose.env` values verbatim: the entrypoint's artifact
  stamp compares the *request* (`args|sandbox|28.5|w1`), so changing `28.5` to the full build would
  re-download. The runner image is pinned by RepoDigest (the service stamp includes the image's
  `StartupHook.dll`), the `sa` password is forced (it lives in the copied `master`). Target volumes
  get `com.docker.compose.project/volume` labels so compose adopts them and `-Remove` deletes them.
- **Admin API:** with `-PortlessRouter`, `Write-RouterFiles` adds `/BC/api/`, `/BC/dev/`,
  `/BC/ODataV4/` at `<Name>.kiri.local`, forwarded with an `Authorization` header. A location with
  its own `proxy_set_header` loses the inherited ones, so Host/Upgrade/Connection are repeated there.
  `proxy_pass $u` with a variable and no URI passes the original (still encoded) request URI. The
  status page's admin cards use these paths; the `.rapidstart` rewrite runs in the browser
  (`DecompressionStream`/`CompressionStream`, UTF-16 kept). `-Update` rewrites `index.html` and the
  router config and reloads nginx.

## Environment facts (maintainer's test machine: Apple Silicon)

- **Engine: Kiri only** (runkiri.com, 0.2.0). Docker Desktop and Podman were removed on 2026-11-14.
  - CLI `~/.kiri/bin/docker` (appended to the END of PATH by `~/.zshrc`/`~/.zprofile`), socket
    `~/.kiri/run/docker.sock`, default context `kiri`, compose/buildx from Kiri.app's cli-plugins.
  - VM: 10 CPUs, 20 GB memory ceiling (`~/.kiri/vm.json`; ballooned, sleeps when idle). amd64 via
    Rosetta. `docker info`: `OperatingSystem: Kiri`, `Architecture: aarch64`.
  - No `credsStore` in `~/.docker/config.json`, so registry logins are stored there in plain form.
  - Validated: BC 29.1 W1 (`latest`) ready in 3 min, `-Remove` leaves nothing behind.
- **ISV apps need a partner license** (`BC_LICENSE_HOST_PATH`). License files are git-ignored and
  only referenced from git-ignored `*.local.env` files.
- **Never swap the SQL container under a running BC tier.** It broke the NST task scheduler
  connection. Recreate the stack, or at least restart `bc` afterwards.
- **First boot and big publishes are slow under emulation:** boot ~3 min, a large ISV app
  publish 220–300 s. Run long commands in the background and poll for the result.

## Company and configuration packages (`-CompanyName`, `-ConfigPackages`)

Working; details and root causes in `docs/ROADMAP.md`. Things that must stay in place:

- **Background tasks** need both fixes the script applies after readiness: the
  `/bc/service/Kernel32.dll` link (task runner's `QueryPerformanceCounter`), and an empty
  `[User].[Windows Security ID]` for the login user (else the task scheduler calls AD natives), which
  needs a tier restart the first time. Symptom of a regression: `importStatus` stuck at `Scheduled`,
  or `Category: TaskScheduling` errors in `logs bc`.
- **Uploads use a rewritten package copy** with `MinCountForAsyncImport="2147483647"`; BC's parallel
  import uses named memory-mapped files (unsupported on Linux).
- **All automation-API calls from the script run inside the bc container** (`Invoke-BcApi`: curl via
  `exec`, bodies and files copied in with `cp`), never through host ports (300 s cut-off) or Kiri
  names (30 s cut-off unless the backend is our router with `proxy_ignore_client_abort`).
- **Company creation needs Full-Text Search:** `-CompanyName` turns on `-FullTextSearch`; on ARM the
  script builds `bclinuxenvironment/mssql:2022-cu17-fts` from its embedded Dockerfile.
- Local test data (git-ignored): `experiments/ls-central-280-demo-data-package/`, the pharmacy release
  folder, and `experiments/Import-ConfigPackages.prototype.ps1` (host-side prototype of the same flow).

## Repository hygiene

The repo is **public**. `experiments/`, `apps/`, `*.app`, `*.bclicense`, `*.local.env` and
`*.rapidstart` are git-ignored (vendor release folders are excluded via `.git/info/exclude`) and must
stay unpublished (proprietary / licensed content). Tracked files must not name license files,
customer/partner identifiers, or vendor package internals; use generic examples
(`./dev.bclicense`, `apps/MyApp.app`). Work there freely, but
don't reference those files from tracked docs as if they were part of the repo; mark them local only.
